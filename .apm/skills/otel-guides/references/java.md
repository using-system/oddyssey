## Planning notes

- Traces, metrics, and logs are all marked **Stable** for OpenTelemetry Java — safe to plan for all three signals without stability caveats.
- The zero-code Java agent is the officially recommended starting point: it auto-detects and instruments a large set of libraries with no code changes, so an instrumentation plan should default to it unless there's a specific reason for manual/library instrumentation.
- Spring Boot apps have a dedicated zero-code option (Spring Boot starter) that layers on top of library instrumentation via Spring autoconfigure — prefer it over the generic Java agent when the target is a Spring Boot service and code-level integration is acceptable.
- JMX metrics collection is a Java-specific capability worth calling out separately in a plan when the target runs on the JVM and exposes MBeans (e.g., JVM internals, application servers).

## Profiling

Cross-language facts — the signal status (Alpha), why a vendor SDK bypasses the Collector, how profiles correlate with traces — live in [profiling.md](profiling.md); this section carries only what is particular to this language. Verified 2026-09-05 against the linked pages.

| Profiler | What it is | What to do with it |
| --- | --- | --- |
| [Pyroscope Java](https://grafana.com/docs/pyroscope/latest/configure-client/language-sdks/java/) | `io.pyroscope:agent` — as `-javaagent:pyroscope.jar` or started from code — built on [async-profiler](https://github.com/async-profiler/async-profiler); configured by `PYROSCOPE_*` variables, system properties, or `pyroscope.properties`. | **The trap**: the default output format is `collapsed`, which carries one event; `PYROSCOPE_FORMAT=jfr` is required for CPU plus allocation plus lock in one agent (`PYROSCOPE_PROFILER_EVENT`, `PYROSCOPE_PROFILER_ALLOC`, `PYROSCOPE_PROFILER_LOCK`). |
| [`pyroscope-otel-javaagent-extension.jar`](https://grafana.com/docs/pyroscope/latest/configure-client/trace-span-profiles/java-span-profiles/) | The OTel Java agent extension (from `grafana/otel-profiling-java`) loaded through `OTEL_JAVAAGENT_EXTENSIONS`; `OTEL_PYROSCOPE_START_PROFILING=true` lets it start the profiler itself. | The trace correlation package: it rides the OTel Java agent the plan already recommends, so one `-javaagent` line plus the extension covers both. |
| Native OTel profiles | The [status page](https://opentelemetry.io/status/index.md) marks Java's Profiles column `Development`: the [`opentelemetry-java` README](https://github.com/open-telemetry/opentelemetry-java#readme) lists `opentelemetry-sdk-profiles` and `opentelemetry-exporter-otlp-profiles` — `1.65.0-alpha` on [Maven Central](https://repo1.maven.org/maven2/io/opentelemetry/opentelemetry-sdk-profiles/maven-metadata.xml) (last updated 2026-08-07; the README's badge lags at `1.64.0-alpha`). Neither the Java agent README nor `opentelemetry-java-contrib` (`JFR Connection`, `JFR Events`, alpha) describes a profiler that fills them. | The only language with any native profiles artifact — an alpha SDK and exporter, not a profiler; do not plan on them producing profiles. |
| [JDK Flight Recorder](https://docs.oracle.com/en/java/javase/21/jfapi/why-use-jfr-api.html) | The JVM's built-in event recorder; Pyroscope ingests its JFR files (`format=jfr`). | The platform baseline when no agent may be added; not continuous by itself. |
