## Planning notes

- Zero-code instrumentation is first-class: the `opentelemetry-instrument` command auto-instruments an app without code changes and is the recommended starting point (covered in Getting Started, not as a separate top-level section).
- Signal status per the docs index: Traces = Stable, Metrics = Stable, Logs = Development — treat log instrumentation as less mature and verify current behavior against the fetched page before relying on it.
- Requires Python 3.10+; base packages are `opentelemetry-api` and `opentelemetry-sdk`, with `opentelemetry-exporter-{exporter}` and `opentelemetry-instrumentation-{name}` as the naming convention for extension packages.
- Manual instrumentation is designed to layer on top of zero-code/automatic instrumentation (linking custom spans/metrics into the auto-instrumented app), not to replace it.
- Hooking code into the zero-code process (field-verified 2026-09-02 and 2026-09-04 against `opentelemetry-distro` / `opentelemetry-instrumentation` 0.65b0, SDK 1.44.0): the distro's `_configure` runs under the wrapper before the target script, while `sys.modules['sitecustomize']` is the wrapper's; it never runs under plain `python`. The plan therefore ships the hook as an `opentelemetry_distro` / `opentelemetry_configurator` entry point (table row above), never as a project `sitecustomize.py`, and names the `OTEL_PYTHON_DISTRO` / `OTEL_PYTHON_CONFIGURATOR` values when more than one is installed.
- Default resource detectors (SDK 1.44.0, [`opentelemetry/sdk/resources/__init__.py`](https://github.com/open-telemetry/opentelemetry-python/blob/v1.44.0/opentelemetry-sdk/src/opentelemetry/sdk/resources/__init__.py), verified 2026-09-05): with `OTEL_EXPERIMENTAL_RESOURCE_DETECTORS` unset, `Resource.create` runs `service_instance` and `otel` only — no `process.*`, `os.*`, `host.*`. `OTEL_EXPERIMENTAL_RESOURCE_DETECTORS=process,os,host` turns on the SDK's own others (the `opentelemetry_resource_detector` entry points in the SDK's `pyproject.toml`: `otel`, `process`, `os`, `host`, `service_instance`); `containerid` comes from the contrib package `opentelemetry-resource-detector-containerid` (0.65b0), `*` expands to every registered detector. Read the source at the pinned tag: the readthedocs `sdk/resources.html` page does not state the default set, and a summarising fetch of it claimed every built-in detector runs — wrong.
- Package `README.rst` files at a tag are stubs — an install line and links (`opentelemetry-sdk` at v1.44.0, `opentelemetry-resource-detector-containerid` at v0.65b0 are twenty lines each). Fetch `__init__.py`'s docstring and `pyproject.toml` (entry points, dependencies) instead; the one README worth reading is `opentelemetry-instrumentation`'s, which documents the wrapper.
- Pinning (mirrors the `otel-instrumentation-expert` rule): resolve versions from the index JSON API first — `curl -s https://pypi.org/pypi/<pkg>/json | jq -r '.info.version'` — and fall back to `pip index versions --pre <pkg>` when a `pip` exists (a uv-managed environment has none: `uv run --frozen pip ...` prints nothing). The whole contrib line (`opentelemetry-distro`, `opentelemetry-instrumentation-*`, `opentelemetry-resource-detector-*`) is pre-release only (`0.xxb0`), so bare `pip index versions opentelemetry-distro` answers `ERROR: No matching distribution found` (reproduced 2026-09-05 with pip 24.3.1; `--pre` answers `0.65b0`) — expected, never "package gone".

## Profiling

Cross-language facts — the signal status (Alpha), why a vendor SDK bypasses the Collector, how profiles correlate with traces — live in [profiling.md](profiling.md); this section carries only what is particular to this language. Verified 2026-09-05 against the linked pages.

| Profiler | What it is | What to do with it |
| --- | --- | --- |
| No native producer | The [status page](https://opentelemetry.io/status/index.md) marks Python's Profiles column `-`; nothing in the Python docs index mentions profiling. | The OTel profiles signal has no Python producer: a plan names the vendor SDK below, never "OTLP profiles". |
| [Pyroscope Python](https://grafana.com/docs/pyroscope/latest/configure-client/language-sdks/python/) | `pyroscope-io` ([1.2.1 on PyPI](https://pypi.org/project/pyroscope-io/)), `pyroscope.configure(application_name=..., server_address=..., tags={...})`; CPU by default, memory with `mem_enabled=True` (not in free-threaded builds); pushes to Pyroscope's own ingest (the local stack's `:4040`), never through the Collector. | The working SDK. **Fork caveat** (the page's own caution): the client starts background threads and is not fork-safe afterwards — call `pyroscope.configure()` only after the last fork, in Gunicorn's `post_fork` hook, never in a module imported under `preload_app`. |
| Tags | Static `tags={...}` at `configure`, dynamic `pyroscope.tag_wrapper({...})` around a block; names must match `[a-zA-Z_][a-zA-Z0-9_]` — no period. | There is no `service.instance.id` equivalent in SDK profiles: mirror the OTel resource attribute as a bounded tag, `tags={"service_instance_id": <the same value the SDK resource carries>}`, so profiles and traces of one instance can be joined (#258). Bounded means one value per process, not per request — tag cardinality is a Pyroscope series. |
| [`pyroscope-otel`](https://grafana.com/docs/pyroscope/latest/configure-client/trace-span-profiles/python-span-profiles/) | `pyroscope.otel.PyroscopeSpanProcessor` ([1.1.0 on PyPI](https://pypi.org/project/pyroscope-otel/)) added to the `TracerProvider`; tags samples with span IDs; its page: "Only CPU profiling is supported at the moment". | The trace correlation package. |
| Under `opentelemetry-instrument` | The profiler bootstrap (`pyroscope.configure` and the span processor) must live in an `opentelemetry_distro` / `opentelemetry_configurator` entry point — see "Hooking code into the zero-code process" above — not in a project `sitecustomize.py`, which the wrapper shadows. | Field-verified 2026-09-02 and 2026-09-04 (distro 0.65b0, SDK 1.44.0): the entry point runs before the target script under the wrapper and never under plain `python`; a hook that raises leaves proxy providers and no signals at all, one swallowed log line. |
