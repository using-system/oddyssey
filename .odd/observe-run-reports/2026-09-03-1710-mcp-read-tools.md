## 4. Improvement opportunities

- **I1 — build the readiness HTTP client once per process (or make its
  cost a span).** Expected gain: −20 to −28 ms per `odd_stack_status`
  call, root p50 ~119 → ~92 ms (−23 %). Proof: fetch a load status trace
  and measure `first GET start − image-inspect end` ≤ 5 ms (before: 27.9
  ms on `529e6be1…`); and spanmetrics
  `histogram_quantile(0.5, sum by (le) (traces_spanmetrics_latency_bucket{service="oddyssey-mcp",span_name="tools/call odd_stack_status"}))`
  ≤ 0.095 (before: 0.097, interpolated; trace-list p50 119 ms is the
  finer number). If a span is added instead, the gain is visibility, not
  time: the new span's duration equals the former gap.
- **I2 — one `docker inspect` for identity and user env.** Expected gain:
  −20 to −25 ms per status call (one of the two ~22 ms inspects). Proof:
  `sum by (span_name) (traces_spanmetrics_calls_total{service="oddyssey-mcp", span_name="oddyssey.docker.inspect"})`
  = 1 x the number of status calls in the store (before: 2 x + the
  reset's 3 → 73 for 35 calls); span tree of a status trace shows 1
  inspect + 1 image-inspect + 4 GET (before: 2 + 1 + 4).
- **I3 — probe the four readiness endpoints concurrently.** Expected gain:
  −6 to −8 ms per call (4 sequential GETs ~10 ms → the slowest ~4 ms);
  smallest of the three, take it only with I1. Proof: the 4 GET spans
  overlap in a fetched trace (before: strictly sequential, +108.0 /
  +112.6 / +114.8 / +116.7 ms).
- Combined I1+I2(+I3): status root p50 ~119 → ~65–75 ms; the client wall
  moves by the same ~50 ms only (F3 dominates it).

## 6. Decisions the spec must settle

1. **Run identity for one-shot processes:** keep one slug per run
   (attributable by name, SDK histograms last-writer-wins — F4) or emit a
   per-process id plus a run-level resource attribute (summable, but
   attribution moves to the new attribute and every stored protocol's
   slug query changes). Spec decision #9 as amended by #148 chose the
   former; F4 quantifies the cost at n=35.
2. **Is `odd_stack_status`'s docker phase worth 20–25 ms?** Identity and
   user env from one `docker inspect` (I2) vs the current two calls, each
   owned by its helper — a maintainability trade the telemetry cannot
   rule.
3. **Where does the readiness client live?** A module-level client (I1)
   changes the server's lifecycle semantics (a long-lived session keeps
   a socket pool); a per-call client with an explicit span keeps
   behavior and buys visibility only.
4. **Is the one-shot lifecycle cost (F3, ~1.12 s/call) in scope?** It is
   the driver protocol's cost; a session-mode benchmark (one server, N
   calls) would measure the service without it — a different scenario,
   not a replay of this one.
