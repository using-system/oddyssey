## 6. Decisions the spec must settle

- **Does the I1+I2 bar (status root p50 ≤ 75 ms) stand, or is 82 ms the new baseline?** The fix delivered −38 ms of an expected −40 to −53; the shortfall is F6's ~15 ms, whose cause is not yet named. Chasing it means a span or a profile first (I1'), then a fix; accepting 82 ms means re-baselining check 1's criterion.
- **Is the remaining interval worth a span even if it is not worth removing?** A span that names 15 ms costs nothing on the request path and turns F6 from suspected to confirmed; the spec decides whether "every ms of a status call is spanned" is a property the loop keeps.
- **`image inspect` on every status call (37.8 ms, 46 % of the root):** cache it on the image id the container inspect returns (I2's next lever), or accept that a status call re-reads the image — a correctness trade-off (a re-pulled image under the same tag) the telemetry cannot rule.
- **What should the lifecycle spans carry?** Zero attributes today. A pid, the transport and the interpreter's start instant would split F8's ~601 ms; the spec decides whether the loop needs that split or accepts the residual as the transport's cost.
- **F7's version lookup:** cache at import or accept 0.4 ms — cosmetic either way; a decision so the next verify does not re-open it.
- **Logs and profiles for `oddyssey-mcp`:** still absent by design (stdout is the wire; no profiler SDK). Recording that as a ledger decision would stop every replay from re-listing them.
