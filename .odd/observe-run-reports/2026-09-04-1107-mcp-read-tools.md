  `src/mcp-server` makes `service.version` equal `pyproject.toml`'s

  `count by (service_version) (target_info{service_instance_id="<slug>"})`

## 6. Decisions the spec must settle

1. **Shared-slug cumulative temporality (F4):** keep the run slug as
   the per-run identity and accept that the SDK histograms describe
   the last process only (the protocol reads spanmetrics and the trace
   list), or give each one-shot process its own `service.instance.id`
   (the SDK's default UUID, opted in) at the price of 70 series per
   run, or switch the exporter to delta temporality so the series sum.
2. **The docker phase (F2, I2):** is a single `docker inspect` (plus a
   cached image inspect) an acceptable change to `odd_stack_status`'s
   contract — the result carries `image`, `created`, `started`, `env`
   today — or is the three-call shape intended for freshness?
3. **The gap (F1, I1):** instrument the interval first (a span naming
   the work) or restructure on the origin report's hypothesis without
   measuring it — the report recommends the span first.
4. **Check 1's band form:** the baseline's `p50 106–135 ms and p95 ≤
   135 ms` band passed here with margin (p50 120, p95 126, max 127); a
   min–max band is still one docker-jitter sample away from a false
   fail (the baseline's O1). Which form does the verify run rule on?
5. **Logs and profiles for this service:** are they wanted at all for
   a stdio one-shot process (the gaps above are absences by design
   until someone decides otherwise)?
6. **Release hygiene (O2):** should the branch's venv be re-synced as
   part of a version bump (a CI or pre-commit step), so
   `service.version` in every branch-build observation matches the
   source at `revision`?
