| [Pyroscope: OpenTelemetry eBPF profiler](https://grafana.com/docs/pyroscope/latest/configure-client/opentelemetry/ebpf-profiler/) | Pyroscope receives OTLP profiles (gRPC on port 4040) from the OTel eBPF profiler running as a Collector with the `profiling` receiver and an `otlp_grpc` exporter, started with `--feature-gates=service.profilesSupport`. Client-side packages exist for Go, Java, Ruby, .NET, and Python; the profile types depend on the language: the Go, .NET, Python, and Ruby pages each say "Only CPU profiling is supported", the Java page says CPU (`itimer`, `cpu`) and wall. | The correlation mechanism to plan when traces and profiles must meet: a vendor package on the tracing side (a `SpanProcessor` or `TracerProvider` wrapper) plus the SDK on the profiling side — see the per-language table. Its warning is worth repeating: dynamic span names embedding per-request identifiers degrade performance. |
| [Pyroscope language SDKs](https://grafana.com/docs/pyroscope/latest/configure-client/language-sdks/) | The SDK list: Go, Java, Python, Ruby, Node.js, .NET, Rust — plus eBPF through Alloy. The [profile types](https://grafana.com/docs/pyroscope/latest/configure-client/profile-types/) page tabulates which profile type each SDK collects (CPU everywhere; memory, mutex, block, lock, wall, heap, exceptions vary). | Pick the SDK row for the language, then read the profile-types table before promising a profile type in a plan — Ruby, Rust, and Node.js collect far fewer kinds than Go, Java, or .NET. |
| [Pyroscope eBPF through Alloy](https://grafana.com/docs/pyroscope/latest/configure-client/grafana-alloy/ebpf/) | Alloy's [`pyroscope.ebpf`](https://grafana.com/docs/alloy/latest/reference/components/pyroscope/pyroscope.ebpf/) component: CPU profiles only, Linux only, root required; natively compiled C/C++, Go, Rust, Zig, and the high-level languages Java (Hotspot), .NET, Python, Ruby, PHP, Node.js, Perl, each with an `<lang>_enabled` flag. No memory or lock profiling. | The no-code fallback for a language without an SDK (C++, PHP, Perl) and the zero-change option for the rest — CPU only. |

## Planning notes

- The signal is Alpha in the specification and `-` for every language SDK but Java (Development, an alpha SDK plus OTLP exporter, no profiler). A plan that promises "OTel profiles" from an application SDK today is promising something the status page does not list — say so, and name the vendor SDK actually doing the work.
- A vendor SDK (Pyroscope's are the concrete case) pushes over the vendor's own push API — Pyroscope's `/push.v1.PusherService/Push` or `POST /ingest` — never OTLP. It therefore bypasses the Collector's OTLP pipeline whatever the language; the OTLP receiver's alpha `profiles` support and the `--feature-gates=service.profilesSupport` pipeline serve the OTel eBPF profiler, not the SDKs. The verification protocol of a profiling plan queries the profiling backend directly (the local stack exposes Pyroscope's ingest on `:4040`), never a Collector pipeline.
- Correlation is a second package on the tracing side (the vendor's span processor or tracer-provider wrapper per language above): plan it explicitly, and only for the profile types its language page lists — CPU for Go, .NET, Python, and Ruby; CPU and wall for Java.
- Pyroscope tag and label names cannot contain a period, so OTel resource attributes are mirrored with underscores (`service_instance_id`); the Python reference carries the bounded-tag pattern.
- The eBPF profilers (OTel's and Alloy's) are the option when the language has no SDK or the code cannot change: Linux, privileged, CPU only. The rest of a plan's profile types (memory, lock, wall) come from an SDK or not at all.
- Re-check the status page's Profiles column before repeating any "-" above: it is the cheapest page here and the one most likely to change.
