## Planning notes

- The docs answer the direct-vs-Collector question explicitly: exporting straight to a backend is a fine way to get value quickly and gives decent results in development or small-scale environments, but in general the project recommends a Collector alongside the service so the app can offload data quickly and the Collector handles retries, batching, encryption, and sensitive-data filtering.
- Starting a Collector is cheap by design: the default OTLP exporters in each language assume a local Collector endpoint, so a Collector launched locally starts receiving telemetry without SDK changes.
- The Collector's overall status is *mixed*; component maturity varies and each component documents its own stability level in its `README.md`. Check the component, not the Collector, before calling something stable.
- Agent and gateway are not exclusive: the agent-to-gateway pattern combines a local Collector per host/pod with a central gateway tier, which is the shape most remote-backend plans converge on.
- Collector-side transformation is the vendor-neutral place to redact or drop data, but it costs performance and adds a deployment to operate — name the specific feature (tail sampling, redaction, retry buffering) that justifies it, or export directly.
