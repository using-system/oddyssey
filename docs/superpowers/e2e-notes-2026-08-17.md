# End-to-end validation — 2026-08-17

Live validation of the full MCP toolchain against real telemetry: stack lifecycle through
`oddyssey_mcp.stack`, the migrated summarizer (`oddyssey_summarize`) integration test, and a real
`odd_baseline` → `odd_diff` cycle through the MCP tool functions.

Everything below is measured. One shared stack lifetime, two fresh uvicorn processes
(N+1 then `ODD_FIXED=1`), 200 sequential `GET /users` per run, 50 users x 5 posts, SQLite.
Stack: `grafana/otel-lgtm:0.30.2`. Protocol per `docs/superpowers/spike-notes-2026-08-17.md`.

## Commands, in order

```bash
# 1. Stack up through the new code path
uv run --project src/mcp-server python -c "from oddyssey_mcp.stack import stack_up; print(stack_up())"
# -> {'running': True, 'grafana_url': 'http://localhost:3000', 'otlp_endpoint': 'http://localhost:4317'}

# 2. Seed and run the instrumented N+1 variant (from examples/n-plus-one; cwd-relative SQLite)
uv run python -m app.seed          # -> seeded 50 users with 5 posts each
env OTEL_SERVICE_NAME=n-plus-one \
    OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 \
    OTEL_SEMCONV_STABILITY_OPT_IN=http \
    OTEL_METRIC_EXPORT_INTERVAL=5000 \
    OTEL_RESOURCE_ATTRIBUTES=service.instance.id=BASELINE \
    uv run opentelemetry-instrument uvicorn app.main:app --port 8000

# 3. Readiness on an unrouted path, then replay the scenario
until [ "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8000/__odd_probe)" = "404" ]; do sleep 0.5; done
uv run python -m app.load          # -> done: 200 requests, 0 errors

# 4. Wait 75 s (>= ~10 s metric flush, ~60 s Tempo searchability), then the integration test
uv run --project src/summarize pytest -c src/summarize/pyproject.toml tests/summarize \
    -m integration -o addopts="" -v
```

```bash
# 5. Baseline through the MCP tool function, into a scratch ODD_DIR outside the repo

# 6. Kill the N+1 app, restart with ODD_FIXED=1 (fresh process, instance FIXED),
```

## Tempo staleness check (per the spike caveat)

The spike found that a Tempo search issued right after a run can return a stale block response.
Both runs were therefore cross-checked: a `GET /api/search` result was compared against a full
`GET /api/traces/<id>` fetch of one trace from the same window.

| Run | search `spanSet.matched` | search `inspectedBytes` | full-fetch spans | full-fetch `db.system` spans |
| --- | --- | --- | --- | --- |
| N+1 | 52 | 328636 | 55 (`GET /users` 1, `GET /users http send` 2, `connect` 1, `SELECT ./demo.db` 51) | 52 |
| fixed | 2 | 42062 | 5 (`GET /users` 1, `GET /users http send` 2, `connect` 1, `SELECT ./demo.db` 1) | 2 |

The two searches returned different `inspectedBytes` and the full fetches confirm the per-trace
counts, so no staleness affected these measurements. 200 traces x 52 = 10400 and 200 x 2 = 400,
matching `db.client.operation.count` in both reports.

## Deviations and observations

1. **No decorator unwrapping needed.** The brief anticipated that `@mcp.tool()` might make the
   functions non-callable. On `mcp==2.0.0` the decorator registers the tool and returns the
   original function object: `type(odd_baseline)` is `<class 'function'>` and `callable(...)` is
   `True`, so `from oddyssey_mcp.server import odd_baseline` and calling it directly works exactly
   as written in the brief. No fallback to the underlying implementations was required.
2. **`http.server.request.count` is 201, not 200.** The 201st request is the readiness probe
   (`GET /__odd_probe`, HTTP 404, and the `"GET"` entry with count 1 in `top_spans`). The
   summarizer intentionally counts the whole service (`job="n-plus-one"`) rather than filtering
   `http_route="/users"` as the spike queries did, so an unrouted probe is included. Identical in
   both runs, so it cancels out of the delta. Not a defect — but it means the count is
   "requests the service handled in the window", probes included.
3. **p95 differs slightly from the spike** (0.0198 s vs 0.02275 s for N+1; 0.0049 s vs 0.00495 s
   for fixed). Different stack lifetime and machine load; the ratio and the DB span counts
   (10400 / 400) reproduce exactly.
4. **`OTEL_RESOURCE_ATTRIBUTES=service.instance.id=BASELINE|FIXED` was kept** from the spike
   protocol for deterministic `instance` labels while inspecting Prometheus by hand. The
   summarizer does not use the `instance` label — it isolates runs purely by time window — so this
   pinning is optional for the tool path.
5. **`test_integration.py`'s module docstring still shows the pre-migration command**
   (`uv run pytest tests/ -m integration -o addopts=""`). The working command is the one used
   above. Known, deferred; no code changed in this task.
6. **No code fixes were needed.** Everything ran green on the first attempt; nothing in
   `src/summarize` or `src/mcp-server` was touched for this validation.
